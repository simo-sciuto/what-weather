# Tavola unica: spikes before the one map (WTH-307, ADR-028; D1 of ADR-029 at the end)

> **Correction (2026-10-19, found by the D1 run):** without a Mapbox token mapbox-gl 3.31 prints "A valid Mapbox access token is required" and draws an empty map, even with an empty style. S1 and S2 below were therefore measured on a map that drew nothing: the numbers (16.7 ms) are not evidence for the real map. S2's finding about the page taking the touch first (the map must be raised above the page when open) is a property of the browser's hit testing and stands. D1 (the end of this file) redid the measure with the real map.

Run 2026-10-19 on the branch `claude/atlas-foundation`. Each answers one question that decides whether C4 (the one map) is safe to build. Scripts here: `s1.html` (a real Mapbox GL map over an empty style, no token, fixed behind a scrolling page, its box clipped by `clip-path`), `s1.mjs` (frame times), `s2.mjs` (touch gestures). To rerun: copy `node_modules/mapbox-gl/dist/mapbox-gl.js` and `.css` next to them and run the `.mjs` files from that directory with Node (they serve the page on a local port and drive the installed Chrome through `playwright-core`).

## S1: clip-path on a fixed WebGL canvas. Passed in Chrome, not yet on Safari or a phone
- The map box opens from a window to the full viewport with `clip-path: inset(...)`, 520 ms, `cubic-bezier(.3, 0, 0, 1)`; no `map.resize()`; the page scrolls over it.
- Frame times in Chrome on this Mac (Intel Iris 6100): 16.7 ms on average, at most 16.8 ms, no frame over 50 ms, in five cases (idle, open, close, open while `flyTo` runs, page scroll), at 1440x900 and at 390x844 with touch and a device pixel ratio of 2.
- Not shown: Safari (the target that matters most), a real phone GPU, a map with real tiles and the weather field's two raster layers (an empty style is light work for the GPU). Criterion for C4: the same numbers on an iPhone with the real map and the field. Until then S1 is a pass in Chrome only.

## S2: gestures against page scroll. Passed in Chrome, and it settled the design
- First run, the map behind the page (`z-index: -1`): with the map "open" a vertical swipe still scrolled the page and the map did not move. The page's boxes get the touch first, whatever `pointer-events` they have.
- Second run, the map raised above the stations when open (`z-index`, `touch-action: none`): the same swipe moved the map (latitude 45.46 to 42.84), the page stayed at 0; a horizontal drag moved it too. Closed, the same swipe scrolled the page (0 to 396) and the map stayed.
- Consequence for the design: when the map opens it goes above the page (and the stations become `inert`); it is not just clipped wider. And on a phone the map in its window cannot be dragged with one finger (that would trap the scroll): in the window it is a picture with a tap to open it, and it is panned only when open. On a computer the window can take wheel and drag. This refines choice 2 of WTH-303 for the phone; say if you disagree.

## S3: one cache key for a cell, with and without a name. Confirmed risk, fix designed, not built
- `load()` in `lib/weather-page.ts` is a `"use cache"` function keyed on all its arguments, `name`, `region` and `country` among them. `/api/atlas/point` calls `weatherFor({ lat, lon })` with no name. The home, given `?lat&lon&name=...`, calls it with a name: another key, so another set of upstream calls (forecast, yesterday, pollen) and, because the region and country are missing, one more place search (`namesFor`). Same coordinates, since `cellOf` and `roundCoord` use the same rounding.
- Today's Atlas to home link avoids it by giving no name unless the point is inside a town (`placeRefOf`, WTH-301), and when it does give one, it pays the second load.
- Fix, for C4 (changes a shared function, so it needs the user's look): key `load()` on the coordinates, the scenario and the hour only; apply the name, region and country after it, outside the cache; cache `namesFor` on its own (name and coordinates). Then the point route, the home, the poster and the saved places all share one entry per cell. Criterion: one set of upstream calls per cell whatever the name; a unit test with a counting provider.

## S4: no server render during map stops. Not measured, by design
- It can only be measured once the map sits in the home. Today `useAtlasEngine` calls `router.replace('/atlas?lat&lon')` on each stop; C4 replaces that with `history.replaceState` (the Next docs for this version say it syncs `useSearchParams` and does not re-run server components; `mode.ts` already uses it on the home). Criterion for C4: ten stops, zero runs of `loadWeatherPage`, one when the place is adopted.

## D1 (WTH-322, ADR-029), run 2026-10-19 with a real Mapbox map (public token from `.env.local`, read at run time, not stored)
Prototypes are in the scratchpad of the session, not in the repository. About 70 map loads were billed to the token for all the runs.

- **V1, glass over the real map: passed in Chrome.** Real Mapbox GL with two coloured raster layers as the weather field, a 360 x 64 bar with blur 16 px, saturation 1.8 and a 0.5 dark layer; about 9 s of continuous movement (a fly out and back, 40 pans, rotation and pitch); 6 alternated laps per variant (the first pass was fooled by the machine's load). Desktop 1440 x 900: opaque, glass and frozen glass all 16.7 ms on average, no frame over 25 ms apart from one or two per lap. Phone 390 x 844 at 2x with the CPU slowed 4x: glass no worse than opaque (16.7 to 17.0 against 16.7 to 19.3). Decision: **full glass (technique A), no frozen glass**; frozen stays as a switch in reserve for Safari. Limits: the Mac's GPU is old but a desktop one; the CPU slowdown does not model a phone's GPU; Safari and iPhone not tried (the main risk is `backdrop-filter` over a WebGL canvas).
- **V2, the transition in one route: passed in Chrome.** Three sections as state in one page, `startTransition` with `addTransitionType` and `<ViewTransition>`; the bar with its own transition name and `pointer-events: none` on `::view-transition`. 9 of 9 transitions ran, the direction was right forward and back, including the browser's Back and Forward buttons. Back/Forward do not carry a type (the docs say so): the direction is worked out in the `popstate` listener from the order of the sections (Meteo, Esplora, Crea), not from the history, so Back from #meteo to #crea moves forward because Crea is to the right. 24 clicks 110 ms apart during running transitions: 24 applied, none skipped. Effective duration 522 to 594 ms (exit 320, enter 500); with reduced motion 39 to 75 ms. To keep the bar still the root snapshot needs `animation: none` on `::view-transition-old(root)`, `new(root)` and `group(root)`. **Not verified:** how the liquid indicator looks inside a named bar during the transition (headless screenshots showed a plateau for 250 ms then a jump, though the DOM animation was smooth): the user's eye is needed; mitigations if it shows are a transition name active only during the transition, or animating the indicator after `ready`.
- **V3, the map stays alive: passed.** The map is made once outside the sections; 10 section changes at phone size: one creation, one WebGL context, the camera unchanged. What costs is not the map but any source that asks for continuous repaint (an animated canvas source, `triggerRepaint`) with its loop: 120 frames a second when hidden, 10 + 14 % of a core, and neither `display: none`, `visibility: hidden` nor `map.stop()` stopped it. Pausing the field (stop its loop, `source.pause()`) brought it to 0 + 1 %; `display: none` also needs `map.resize()` on return. Re-creating the map on every visit costs 0.5 to 1.2 s and a billed load each time, loses the WebGL context, and raced (10 quick changes made 4 to 6 instances). Decision: **one map always mounted, the field paused when Esplora is hidden.**
- **Risks for the product code:** Esplora must be transparent to show the map under it, and on leaving Meteo the map appears at once under the sliding section (it sits in the root snapshot): it needs its own transition name or a cover; no `typeof window` branches in the initial HTML of the map's container (a hydration mismatch showed in the prototype); in dev `reactStrictMode` runs the creation effect twice (a guard `if (inst.current)` and `remove()` in the cleanup; the creation counter reads 2 in dev); the animated field must expose `pause` and `play` to the map context (ADR-008); a section's local state (the draft in Create) is lost when it unmounts, so Create and Esplora use `<Activity>` as ADR-029 says; the old S1 above is to be repeated with a token when the map goes into the page (D6a).
